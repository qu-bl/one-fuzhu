# 云端规则与三端实现核对（2026-09-29）

## 结论与范围

基线：云端契约 10.5.4（提交 b1811b1），三端当前工作区。**尚未严格对齐，不能作为全面稳定或上线验收结论。**

本次只核对、复现和记录，没有修改或发布业务规则，没有提交三端代码。核对覆盖：UI 声明检查、资源包错误收集、应用脚本注解、原生默认值消费。没有对三台设备作完整交互测试，没有获取用户应用沙盒中的实际脚本及保存数据。

证据分为两类：检查器问题运行当前 contract.inspection.program 复现；原生差异通过当前源代码路径对照确认，尚未逐项在真机重现。

## 确认的问题

### 1. 身份、定时注解仍会读取说明文字（高优先级，已执行复现）

输入：
```js
/**
 * 使用 @id Wrong 作为示例
 * @id Correct
 */
defineQuScript({});
```
实际结果：检查无错误，metadata.identity 为 Wrong，应读取显式声明 Correct。

把说明换成 `使用 @interval 1 作为示例`，后面正式声明 `@interval 1000`，实际仍按 1 报错。10.5.4 只修正了 observe；id/interval 的 capture 仍搜索任意位置。

影响：身份关系到脚本运行作用域和存储定位，不能只视为文案问题。
位置：inspection/inspector.mjs 的 capture。
处理方向：用一套明确的声明识别方式处理所有注解，保留合法注解用法，不继续逐个关键词补丁。

### 2. 非法字段导致检查器异常，而非汇总错误（已执行复现）

资源包声明 observe 为 device.*，某条 binding.qu 为数字 123。
JSON Schema 已能指出 qu 不是字符串，但语义检查继续执行 `b.qu?.startsWith(...)`，产生 TypeError，整次请求丢失正常 errors 返回。

位置：inspection/inspector.mjs，manifest 中 declared 计算。
处理方向：语义检查仅在所需字段类型成立时执行；保留其他位置的错误收集。这是检查程序健壮性修复，不应新增作者约束。

### 3. 安卓忽略 visible 的 false 回退值（源代码确认）

合法声明：`bindings.visible = {path:"app.ready", equals:true, fallback:false}`。
在字段值尚未可用时：
- Apple conditionMet 使用 condition.fallback；
- 鸿蒙 connect 使用 bindings.visible.fallback；
- 安卓 isVisible 在 boundValues 缺值时直接返回 true。

规范依据：UI_PROTOCOL.md“动态值暂不可用时使用 fallback 或静态值”。
位置：Android QuUIRenderer.kt 的 isVisible；Apple QuUIRenderer.swift 的 conditionMet；Harmony QuUIRenderer.ets 的 connect。
处理方向：安卓消费已有 fallback，不增加新的字段或校验。

### 4. 鸿蒙动态选项尚未到达时忽略默认列表（源代码确认）

合法声明：choice 具有 bindings.options.path 与非空 fallback。
云端会把 fallback 规范化到缺失的静态 options。鸿蒙只要存在动态 path，displayOptions 就返回 boundOptions；其初值为 []，不会取 component.options。

影响：默认可选项在绑定值尚未到达时不显示；这份声明本身可通过检查。
位置：Harmony QuUIRenderer.ets，boundOptions 初始化、connect、displayOptions。
处理方向：区分“尚未收到值”和“已收到空列表”，前者使用默认值，后者保留作者主动清空的含义。

### 5. 静态空选项数组的解码优先级不一致（检查器复现 + 源代码确认）

输入 choice.options=[]，同时 bindings.options.fallback=[{label:"默认",value:"a"}]。
云端检查通过，返回 options=[]。
- Apple 使用 decodeIfPresent ?? fallback，保留显式空数组；
- 安卓使用 .ifEmpty { fallback }，变成非空数组。

位置：Apple QuUIModels.swift 的 options 解码；Android QuUISetValidator.kt 的 decodedOptions。
处理方向：统一缺失值与显式空值的语义，不能把所有空值都等同于未提供。

## 规范本身需要澄清的冲突

### 6. 未知绑定键的警告/拒绝策略不一致（已执行复现）

compatibility.unknownObjectFields=warn，UI 文档称未知第三方扩展只警告；但 bindings 的 Schema 明确 additionalProperties=false。

输入 text.bindings.vendorInfo={path:"app.extra"}：实际是阻断错误。普通组件的 vendorInfo 扩展则走警告。

同时规范又规定每种组件可用绑定由 bindingsByType 决定。因此应明确区分“已知绑定用错组件”与“完全未知扩展键”，不能直接把所有绑定检查放宽，也不能把当前行为称为全局统一的未知字段策略。
位置：generate_schema.py 的 properties["bindings"]；contract.compatibility；UI_PROTOCOL.md“已删除的差异字段”。

## 建议处理顺序

1. 修复身份/定时注解误读和异常打断。
2. 统一三端已有默认值及显式空值语义。
3. 澄清未知绑定扩展策略，依据现有兼容性要求执行，不新增功能。
4. 使用现有作者脚本及其真实保存数据回归，再发布规则和对应客户端；不要为了让新检查通过而要求作者缩短正文或改写正常业务。
